# issue 2 進行速度(tick_interval_ms)の変更機能: プレイヤーが稼働中に変更・最速モード

英語版: `2_tick_speed_control_en.md`(内容が違うときは、この日本語版が正)

**状態: 実装済み(2026-11-14)。結果は末尾「実装結果」** 仕様: `docs/spec/time-spec.md` §6(サーバごとの速さの調整【確定】)。issue #2。TODO G-22(稼働中の変更)を含む。

## 目的
ゲームの進む速さ(1 tick の実時間 `tick_interval_ms`)を、**プレイヤーが、稼働中に、CLI の設定画面から変更できる**ようにする。**0 は「待たずに最速」**(シミュレーションモード)。クライアントが接続していても、最速にできる。現在の値は、凡例の画面(`h`)で確認できる。

## 確定事項(作者指示 2026-11-14)
1. **変更できる人**: プレイヤー全員。**いずれは、プレイヤーの合意や、管理者による変更も導入する**(今回は、権限の判定を 1 か所にまとめて、差し替えられるようにする)
2. **稼働中に変更できる**。プレイヤーが、CLI の設定(`c`)から変更する。**現在の `tick_interval_ms` は、凡例の画面(`h`)で確認できる**
3. **最速モード**(`tick_interval_ms = 0`)は、クライアントが接続していても使える。接続しているプレイヤーが、最速モードを指定できる
4. 値は **0 以上の整数(ms)。上限は 1000 ms(1 秒)**

## 現状(コードから)
- 待ちは、`GameServer.run()` の `asyncio.sleep(delay)` だけ。エンジン(`World.tick()`)は、実時間に依存しない(乱数も tick から決まるので、速さを変えても、結果は変わらない)
- `core/config.py` は、`tick_interval_ms` を「正の整数」とし、20〜200 ms の外は警告。起動時の値だけで、稼働中の変更はない
- 毎 tick、ロングポーリングの待機を起こす(`_tick_event`)。イベントのリングバッファは 20,000 件
- 1 tick の処理は約 0.9 ms(標準の世界)。最速で、毎秒約 1,100 tick(標準の約 55 倍)の見込み

## 仕様

### 値と検査
- `tick_interval_ms`: **整数、0〜1000**。`bool`・小数・負数・1000 超は拒否(422)。環境変数 `ECOLOGRID_TICK_INTERVAL_MS` も同じ範囲(起動時の初期値)
- `0` = 最速(待たない)。1〜19 は、処理が間に合わない可能性があるので、警告(0 は警告なし)。20〜200 が推奨範囲(従来どおり)
- 最速の間、`behind_count` は数えない(遅れではないため)

### 変更の API
- `PUT /api/v1/world/tick-interval`(プレイヤーの認証)。本文 `{"tick_interval_ms": 整数}`。応答 `{"tick_interval_ms": 新しい値, "previous": 前の値}`
- **権限の判定は 1 つの関数**(`can_change_tick_interval(player_id)`)にまとめる。**今は、全プレイヤーに許可**。将来、合意(投票)・管理者の変更に差し替える(管理者は、`X-Admin-Key` でも変更できる拡張を想定)
- **濫用の対策**: 変更は、全プレイヤーを通じて、実時間 1 秒に 1 回まで(超えたら 429)。変更は、全員に通知する(下記)
- 現在の値の取得: `GET /config` の `tick.tick_interval_ms` は、**現在の値**にする。あわせて `limits` に `tick_interval_ms_min`(0)・`tick_interval_ms_max`(1000)を足す。`/healthz` にも、現在の値を足す(クライアントの突き合わせ用)

### 全員に届くイベント
- `tick_interval_changed`: `{player_id, name, previous, tick_interval_ms}`。**知覚の範囲に関係なく、全プレイヤーに届く**(今の `visible_events` は、範囲内だけを通すので、「全員向け」の種類を新設する)
- CLI のログに、「`<名前>` changed the tick interval: 50 → 0 ms (max speed)」のように出す

### サーバのループ
- 1 tick ごとに、現在の値を読み直す。値が変わったら、基準の時刻(`nxt`)を現在に合わせ直す(0 から正の値に戻したときも)
- **最速のときの動作**(CPU の占有と API の応答の両立): 連続して tick を実行し、**実時間で約 5 ms ごとに、1 回、イベントループに制御を返す**(`asyncio.sleep(0)`)。HTTP リクエストは、最大でも約 5 ms の待ちで処理される
- **通知の間引き**: ロングポーリングを起こすのは、実時間で最短 20 ms に 1 回(`tick_interval_ms` が 20 未満のとき。標準の 50 ms では、従来どおり、毎 tick)。起こされた時点までのイベントを、まとめて返す
- イベントのリングバッファの大きさは、最速での測定で決める(必要なら 20,000 から増やす)

### CLI
- **設定画面(`c`)**: 項目を選ぶ(1: 名前、2: tick の間隔)。tick の間隔は、`0`〜`1000` を入力(`max` も 0 として受け付ける)。現在の値と範囲を表示し、エラー(範囲外・429)は、画面に出して再入力。空入力で中止
- **凡例の画面(`h`)**: 「Tick: 50 ms」のように現在の値を表示。0 は「Tick: max speed」。標準(50 ms)との倍率(例: ×1、最速は「max」)も表示する
- 現在の値の更新: `tick_interval_changed` のイベントと、定期の突き合わせ(`/healthz`、3 秒ごと)で、`Session` の値を更新。`step_seconds` は、更新後の値から計算し、下限(例: 1 ms)を設ける。ボットの待ちは、これを使う

## 完了条件(テスト)
- 0 と 1000 を受け付け、-1・1001・小数・`true` は拒否(422)。環境変数も同様
- 稼働中の変更で、間隔が変わる。0 にすると、待たずに進み(同じ時間で、標準より多くの tick が進む)、`behind_count` が増えない。0 から正の値に戻せる
- 1 秒以内の 2 回目の変更は、429
- `tick_interval_changed` が、範囲外のプレイヤーにも届く。`/config`・`/healthz` が現在値を返す
- 速さを変えても、同じ seed で、同じ tick の世界の状態が同じ(決定性)
- 最速のとき、HTTP のリクエストが、遅延の上限内で処理される(測定)
- CLI: 設定画面で、名前と tick の間隔を選べる。範囲外・使用中・429 のエラーを表示して、再入力できる。凡例の画面に現在の値が出る。`tick_interval_changed` で、表示が更新される
- 全体のテストが通る

## リスク
- **濫用**: 誰でも変更でき、他のプレイヤーのゲームも、同時に速く/遅くなる。1 秒 1 回の制限と、全員への通知で緩和。将来の合意・管理者の導入で、根本の対策にする
- **CPU の占有**: 最速は、1 コアを使い切る。5 ms ごとに制御を返すが、同じマシンの他のサービスへの影響は、測定して確認する
- **クライアントの追従**: 最速では、人間が操作できない(Player の 1 歩 = 5 tick = 約 5 ms)。通知の間引きで、サーバの負荷は抑えるが、描画は、クライアントの側の限界がある
- **イベントの取りこぼし**: 間引きで緩和するが、残る場合は、リングバッファを増やす、または、クライアントが view を取り直す
- **放置の判定**: `player_idle_timeout_sec`(実時間 300 秒)は、最速では、ゲーム内の時間が長くなる(動作の問題ではない)

## 範囲外(今回はしない)
プレイヤーの合意(投票)による変更、管理者のみの変更、一時停止・1 tick ずつの進行、変更の永続化(再起動すると、初期値に戻る)、`simulate` ツールのオプション(すでに最速)。

## 実装結果(2026-11-14)
- **21a**: `core/config.py` に `check_tick_interval`(整数の 0〜1000。bool・小数・範囲外は拒否)と定数。0 は警告なし、1〜19・200 超は警告。`GameServer` が現在の値を持ち(`world.cfg.tick_interval_ms` を更新)、`run()` が毎 tick 読み直す。変更したら基準の時刻を合わせ直す(`_rebase`)。最速(0)では待たず、`behind_count` を数えない。環境変数 `ECOLOGRID_TICK_INTERVAL_MS` も 0 を許可
- **21b**: `PUT /api/v1/world/tick-interval`(`{tick_interval_ms}`。422・429(`Retry-After`)・403)。権限は `GameServer.can_change_tick_interval`(今は全プレイヤー)。全プレイヤーを通じて 1 秒に 1 回まで。**全員向けのイベント** `tick_interval_changed`(`World.emit_global`・`World.GLOBAL_EVENTS`。`visible_events` は範囲外・死亡中のプレイヤーにも通す)。`/healthz` に現在値、`/config` の `tick.tick_interval_ms` は現在値、`limits` に `tick_interval_ms_min/max`
- **21c**: 最速のとき、実時間で約 5 ms ごとにイベントループへ制御を返す(`FAST_YIELD_SEC`)。ロングポーリングを起こすのは、20 ms 未満の間隔では、実時間で 20 ms に 1 回(`NOTIFY_MIN_SEC`)。**`World.events_since` を、新しい側から `since` に届くまでだけ見る形に変更**(全件の走査をやめた。標準の速さでも効く)
- **21d**: CLI の設定画面(`c`)を、項目の選択(1: 名前、2: tick の間隔)に変更(`rename_screen`・`tick_screen`・`config_screen`)。0〜1000 または `max`。範囲外・429・403 のメッセージを出して再入力。凡例の画面(`h`)に `Tick: 50 ms (x1)`(最速は `Tick: 0 ms (max speed)`)。`tick_interval_changed` と、3 秒ごとの `/healthz` の突き合わせで更新。`step_seconds` に下限(1 ms)
- **サイドパネル(Side Panel)**(2026-11-14 追記): マップの横の領域(Help の凡例のあった場所)を「サイドパネル」と命名し、`h` = Help、`c` = **Config**(名前・tick の間隔)を、パネルの中で入力する形にした(`cli/ecologrid_cli/panel.py`。キーは 1 つずつ受け取る。`q` や移動のキーも、文字として入力できる。UTF-8 の全角文字も可)。端末が狭いとき(幅 76 桁未満)は、従来の画面全体の入力。擬似端末で、`c`→`2`→`max`→Enter→`1`→名前→Enter→Esc→`h`→`q` の一連を確認した
- **表示の不具合の修正**(2026-11-15。サイドパネルを出していないときに、1 行余白が挟まれたように見える): 原因は、地図の幅・高さを奇数にそろえる処理(`| 1`)が、端末の大きさを超えていたこと(行数が端末より 1 多くてスクロール。端末の幅の半分が偶数だと、各行が 2 桁はみ出して折り返す)。最下行のキー一覧(約 99 桁)の折り返しも原因。**直し方**: 地図は、端末に収まる最大の奇数(`odd_at_most`)、地図以外の行は 11 行分を確保、全行を端末の幅に収める(`clip`。色の指定は桁に数えない)、状態バーの幅と最下行のキー一覧を、端末の幅に合わせて縮める。端末の幅 40〜240 × 高さ 16〜41 × 各ページ(なし・Help・Config)で、幅・行数が端末を超えないテストを追加(TODO C-1 を解消)
