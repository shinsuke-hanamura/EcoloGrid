# tick を 3.3 ms / 5 ms にできるか: 実現可能性の検討

**決定(2026-10-29): tick = 50 ms(仕様 C)。仕様 A・B は採用しない。§8 を参照。** 以下は A・B の検討記録。

2026-10-29。仕様の出典: `docs/spec/voxel-spec.md` §5.2・§5.5。**実装は未着手。** 数値は実測と、実測に基づく試算(試算は明記)。

## 1. 検討する仕様

1 ボクセル = 1 m。最高速度は 1 tick に 1 ボクセル進む速度。

| | 仕様 A | 仕様 B |
|---|---|---|
| tick の長さ(= 1 tick の処理時間の予算) | **3.33 ms** | **5 ms** |
| 最高速度 | 300 m/s(時速 1080 km) | 200 m/s(時速 720 km) |
| 1 ゲーム秒の tick 数 | 300 | 200 |
| 現行(参考) | tick 0.2 秒、1 秒 5 tick、最高速度 5 m/s | |

仕様 B で最高速度を 300 m/s に保つと 1 tick に 1.5 ボクセル進み、「1 tick に最大 1 ボクセル」の前提が崩れる。B の最高速度は 200 m/s になる。

## 2. 現在の実装の実測

環境: T640(Xeon Bronze 3204 @ 1.9 GHz、6 コア)、Python 3.12(Docker)、サーバ停止中、負荷ほぼなし。世界は 4×4 Region(128×128)、初期個体から 600 tick 進めた状態(Grass 3058 / Wheat 237 / Rabbit 134 / Fox 27 / Seed 517、計約 4000)。ボクセル化・水量モデルの前の実装。

| 項目 | 測定結果 |
|---|---|
| **1 tick の処理時間** | 平均 **32.8 ms**、p50 31.0、p99 63.2、最大 69.3 |
| 空の世界(個体なし、16 Region)の 1 tick(下限) | **256 µs** |
| 1 個体の tick 1 回 | Grass 6.7 µs / Wheat 6.9 µs / **Rabbit 62 µs** / **Fox 119 µs** / Seed 0.9 µs |
| 内訳(100 tick) | 植物の `tick` と `_metabolize`、`min`/`max` の呼び出しが上位を占める |
| イベント発生量 | 40 件/tick(0.2 秒)= **約 200 件/ゲーム秒**(`entity_moved` 約 66%、`entity_removed` 15%、`entity_spawned` 13%) |
| **GC の停止** | 管理対象 25 万オブジェクトで、`gc.collect(0)` 0.8 ms、`gc.collect(1)` 0.7 ms、**`gc.collect(2)`(完全)125.6 ms** |
| **タイマーの精度**(`asyncio.sleep` を絶対時刻で積み上げ、空の処理) | 周期 3.33 ms: 遅れ 平均 **0.74 ms**、p99 1.22 ms、最大 2.00 ms。周期 5 ms: 平均 0.74 ms、p99 1.24 ms |

## 3. 現在の方式(全個体を毎 tick 処理)の結論

| | 仕様 A | 仕様 B |
|---|---|---|
| 予算 | 3.33 ms | 5 ms |
| タイマーの遅れ(平均 0.74 ms)を引いた実効予算 | 約 2.6 ms | 約 4.3 ms |
| 現行の 1 tick(平均 32.8 ms)との比 | **約 10 倍(実効で約 13 倍)の超過** | **約 6.6 倍(実効で約 7.6 倍)の超過** |
| 1 ゲーム秒に必要な CPU 時間(32.8 ms × tick 数) | 約 9.8 秒(1 コア 984%) | 約 6.6 秒(656%) |

**現在の方式のままでは、A も B も実現できない。** tick を短くしても「全個体を毎 tick 処理する」方式のままだと、ゲーム時間 1 秒あたりの処理量が 60 倍(A は 300/5)に増える。個体を増やすほど悪化する。さらに、GC の完全収集(125 ms)は、1 回で 38 tick(A)/ 25 tick(B)分の遅れを生む。

## 4. 実現するための方針

**tick を短くすると、「毎 tick 全員を更新する」方式は成り立たない。tick あたりの処理量が、個体の総数ではなく、その tick に実際に起きるイベントの数で決まる方式(イベント駆動)に変える。**

### 4.1 イベント駆動・遅延評価のエンジン
- **次に何かが起きる tick を予約する**(最小ヒープまたはタイマーホイール)。tick ごとに、その tick に期日の来たイベントだけを処理する。既存の個体単位の定期アクション(spec.md §10、タイマーホイール)の考え方を全体に広げる。
- **連続的に変わる状態は、触るときにまとめて計算する(遅延評価)**: Hydration / Energy の減少、植物の Energy の増加などは、毎 tick 更新せず、「最後に更新した tick」を持ち、必要なとき(捕食、判定、予測した閾値の到達 tick)に経過 tick 数から計算する。植物は、毎 tick の処理がゼロになる(種子散布・枯死の予約だけ)。
- 動物の移動は、速度から「次に 1 ボクセル進む tick」を予約する(Rabbit 2 m/s は A で約 150 tick ごと)。**落下中・流水中のように、毎 tick 動く個体だけ**を高速な活性集合に入れる(水は `docs/spec/voxel-spec.md` §4.1 の活性集合)。
- **試算**(現在の 1 回あたりのコストが変わらないと仮定した推定。未検証):
  - 動物の行動: Rabbit 221 匹 × 2 歩/秒 + Fox 28 匹 × 3 歩/秒 ≈ 526 回/ゲーム秒 × 約 70 µs ≈ **37 ms/ゲーム秒**
  - 植物の種子散布: 約 225 回/ゲーム秒 × 約 20 µs ≈ 4.5 ms、繁殖判定・発芽など ≈ 3 ms
  - tick の下限(空 tick 256 µs → 次の期日まで何もしない最適化で約 20 µs と仮定)× 300 ≈ 6 ms
  - 合計 **約 50〜60 ms/ゲーム秒 = 1 コアの約 5〜6%**。1 tick の平均は A で約 0.2 ms、B で約 0.3 ms。
  - したがって、平均の処理量は予算(3.3 ms / 5 ms)に十分収まる。**問題は平均ではなく、最悪値(p99.9)と停止(GC、タイマー、API)**。

### 4.2 エンジンと API を別プロセスにする
- 現在は、API(FastAPI)と tick が同じイベントループで動く。プレイヤー 100 人が毎秒数回ずつ API を呼ぶと、1 秒に数百〜1000 リクエスト(FastAPI で 1 件 0.3〜1 ms と見て、1 コアの 30〜100%)が、tick と競合する。スナップショット(JSON 数十 ms)が 1 つ入るだけで、3.3 ms の予算を何十回も超える。
- **エンジン(tick のみ)のプロセスと、API/ゲートウェイのプロセスを分離**し、イベントを Valkey Streams などで受け渡す(`docs/spec/architecture.md` §5 の方針と一致)。エンジンは API の負荷から隔離される。

### 4.3 配信を間引く
- 200〜300 tick/秒の全イベントをクライアントに配る必要はない(CLI の描画も 10〜30 Hz で足りる)。**ゲートウェイでイベントをまとめる**: 同じ個体の連続する移動は最後の位置だけ、水量の変化も最後の値だけ。落下の描画は、ボクセルを移るたびの位置イベントで足りる(落下 8 ボクセルでイベント 8 件)。

### 4.4 GC・タイマーの制御
- **GC**: 完全収集(125 ms)を、tick の最中に起こさない。生成後に `gc.freeze()`、世代の閾値の引き上げ、tick の合間(余裕のある時間)に世代 0/1 だけを実行、世代 2 は止めて低頻度に手動で行う(その間だけ遅延を許容する)など。Python 3.14 の増分 GC の利用(要確認)。オブジェクトを減らす(`__slots__`、配列化)。
- **タイマー**: `asyncio.sleep` の遅れ(平均 0.74 ms)は、3.3 ms の約 22%。「期日の 1 ms 前までスリープし、残りはビジーウェイト」にする。エンジン専用プロセス・専用コア(`taskset`)・必要なら優先度の引き上げ(`SCHED_FIFO` は特権が必要)。

### 4.5 並列化・高速化の余地(必要なら)
- Region ごとに独立して tick できる設計なので、Region 単位でプロセスを分けて並列化できる(Region 境界はメッセージ)。
- ホットパスの Rust / C 拡張化(PyO3 など)、または Rust / Go でエンジンを書き直す。

## 5. 結論: 実現できそうか

| | 現在の実装 | 再設計(Python) | 再設計(コンパイル言語) |
|---|---|---|---|
| **仕様 A(3.3 ms)** | **不可**(約 10 倍の超過) | **可能性あり・高リスク**。平均の負荷は低い(試算で 1 tick 0.2 ms)が、実効予算が約 2.6 ms で、GC・タイマーの揺れ・p99.9 の余裕が薄い。**試作で確認が必要。** | 実現可能(余裕あり) |
| **仕様 B(5 ms)** | **不可**(約 6.6 倍の超過) | **実現の見込みが高い**。実効予算が約 4.3 ms で、A より約 1.6 倍の余裕。 | 余裕あり |

- A と B の差は、予算の 1.5 倍の余裕と、最高速度(300 対 200 m/s)。ゲーム性の違いは、最高速度に達しない範囲(落下 8 m で着地速度 13 m/s)では、ほぼ無い。tick が長いほど、水の流れ・落下の見た目の滑らかさは A のほうが上。
- **推奨**: 設計は A・B のどちらにも対応できるようにし(tick の長さと最高速度を設定値にする。時間に依存するパラメータは秒で定義して tick に換算する)、**先に試作(スパイク)で p50 / p99 / p99.9 を測って決める**。Python で B を確実に、A を挑戦的な目標とする。
- 成功基準の案: 合成負荷(個体 5000、プレイヤー 100、API の負荷を別プロセスで)で、**tick 処理の p99.9 が予算の 60% 以下**、予算超過(遅れ)が 0.1% 未満。

## 6. 次の一手(試作・スパイク)

`docs/tasks/x_12_realtime_engine_spike.md`。最小のイベント駆動エンジン(ヒープ + 遅延評価、5000 個体)を作り、次を測る。

1. tick の処理時間の分布(A: 3.33 ms、B: 5 ms)。
2. GC を制御した場合の最悪値(p99.9、最大)。
3. 専用プロセス + ビジーウェイトのタイマーの精度。
4. エンジンと API を分離した場合のイベント受け渡しの遅延とスループット。
5. 既存の挙動(捕食・繁殖・移動の統計)がイベント駆動版でも保たれるか(同じ seed での個体数の推移を比較)。

## 7. 注意

- 試算(4.1)は、現行の 1 回あたりのコストが変わらないという仮定の推定。実測ではない。
- 測定は 1 台の CPU(1.9 GHz の Xeon)での値。より高速な CPU ならコストは下がる。
- ボクセル化(3 次元化、水量)で、1 個体・1 ボクセルあたりのコストは増える。水の流れは活性集合で、静止した水は処理しない設計が前提。

## 8. 決定: tick 50 ms(仕様 C)

作者決定(2026-10-29)。1 tick = 50 ms(1 秒 20 tick)、最高速度 20 m/s(時速 72 km)。動きの速さは体感で決め、ゲーム内時間の倍率を掛けない(`docs/spec/time-spec.md`)。

### 余裕の評価(実測に基づく)
| 項目 | 実測 / 予算 50 ms |
|---|---|
| 現行の 1 tick 平均 | 32.8 ms = **予算の 66%** |
| 現行の p99 / 最大 | 63.2 ms / 69.3 ms = **予算を超える** |
| GC の完全収集 | 125.6 ms = 予算の 2.5 倍(1 回で約 2.5 tick 分の遅れ) |
| タイマーの遅れ(`asyncio.sleep`) | 平均 0.74 ms(予算の 1.5%)。問題なし |
| 空の世界の 1 tick | 256 µs(予算の 0.5%) |

- **平均では収まるが、p99 とボクセル化後の負荷増(植物の増加、3 次元の判定)を考えると「安全」とまでは言えない**。1 つの原因は植物: 約 3,200 個 × 約 7 µs ≈ 22 ms で、1 tick の約 2/3。
- 軽量化の見込み(推定、未検証): ①**植物の遅延評価**(毎 tick の更新をやめ、触るときと予約した tick にだけ計算する)で、1 tick の処理は約 33 ms → 約 10 ms(予算の 20%)。②動物の移動を N tick ごとの予約にする(`move_interval_ticks`)ことで、Rabbit 20 tick・Fox 12 tick ごとの処理になり、動物の毎 tick のコスト(約 17 ms)がさらに 1/10 程度に。③GC の制御(`gc.freeze()`、世代 2 の手動実行)で完全収集の遅延を避ける。
- 仕様 A/B で必要だった**大規模な再設計(エンジンと API の別プロセス化、ビジーウェイトのタイマー)は、必須ではなくなる**。API とエンジンが同じプロセスにある現行の構成でも、軽量化 ①〜③ で p99 を予算内に収められる見込み(測定で確認する)。プレイヤー 100 人の API 負荷が大きい場合は、別プロセス化を検討する。
- したがって `docs/tasks/x_12` は、スパイク(試作)ではなく、**軽量化と測定**に縮小する。
