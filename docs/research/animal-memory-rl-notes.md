# 記憶システムへの強化学習(RL)の知見の応用(検討メモ)

作成: 2026-11-08(作者指示)。**検討のみ。実装は指示待ち。** 前提: `docs/spec/animal-memory-spec.md`。将来、NPC の行動を強化学習で強化する可能性がある。記憶システムを RL の概念に対応づけて設計すると、後で学習を乗せやすい。

## 1. 対応表(RL ↔ Ecologrid)
| RL の概念 | Ecologrid での対応 | 備考 |
|---|---|---|
| エージェント | 動物の個体(NPC の Rabbit・Fox。将来 NPC の人間) | PC は、人間が方策の役 |
| 環境 | World / Region(地形・植物・他の個体・気温・時刻) | tick で進む。決定論 |
| 状態 s | 内部状態(水分・Energy・体力・スタミナ・覚醒度)+ 位置 + **知覚した地図(`PerceptMap`。見ることで更新)** + 記憶 | 視界が担当 Region 内に限られ、遠くが見えない → **部分観測(POMDP)** |
| 観測 o | 視界内の地形・個体、足元(**「見る」は action ではなく、観測。結果は地図(状態)の更新**) | 地図は「過去の観測の要約」= 信念状態 |
| 行動 a | 移動(4 方向)・食べる・飲む・休憩・待機 | 離散 |
| 報酬 r | 記憶の reward = (Action, Outcome)の表(種ごとに固定。作者指示)。学習用の報酬は別に検討(§7) | **恒常性報酬**を提案(§4 A) |
| 方策 π | `ai.think`(ルールベース) | ベースラインとして残す |
| 価値 V / Q | (未定義)記憶した場所の「良さ」 | 長期記憶が価値表に当たる(§4 C) |
| エピソード | 個体の一生(誕生 → 死) | 個体が連続して生きる |
| 経験 (s, a, r, s') | 記憶 1 件(`Experience`) | 状態は場所に圧縮 |
| 経験再生バッファ | **短期記憶(未整理のバッファ)** | 上限なし。寝たら整理して空になる |
| 再生(リプレイ) | **入眠時の整理** | 睡眠中のリプレイで、記憶を固定する(神経科学の類比。RL の experience replay にも対応) |
| 認知地図 / 世界モデル | **長期記憶**(場所ごとの結果) | モデルベース RL(Dyna)の「モデル」 |

## 2. 命名(RL の用語から)
`Action` に対する「環境の応答」は、RL では **observation(観測)と reward(報酬)**。
| 候補 | 評価 |
|---|---|
| **`Outcome`(カテゴリ)+ `reward`(数値)** | **推奨**。結果の種類(`drank`・`saw_water`)と、その良さ(数値)を分ける。RL の (o, r) に対応。意思決定理論でも outcome と言う |
| `Response` | 刺激–反応(行動心理学)の用語。RL では使わず、コードの HTTP `Response` と紛らわしい |
| `Feedback` | 一般的。RL でも通じるが、カテゴリと数値の区別がない |
| `Observation` | 知覚(`saw_*`)にだけ合う。`drank` などを含めにくい |
- 記憶 1 件は **`Experience`**(RL の経験)。`Action`・`Outcome`・`reward`・場所・tick・強さを持つ。
- 行動心理学の ABC(Antecedent–Behavior–Consequence)、オペラント条件づけ(強化・弱化)が、RL の源流。`reward` が正なら強化、負なら弱化に当たる。

## 3. 現仕様との整合(最小の拡張)
現仕様の記憶(`Experience`)に、**任意の `reward` 項目を予約**しておけば、RL の検討を後から乗せられる(今は使わない)。さらに、次を差し替え可能にしておく。
- 強さの決め方(`strength_mode`): `random`(現仕様。0〜1 の乱数 × 倍率)/ `reward`(報酬の大きさ)/ `surprise`(驚き)。
- 想起の score(`strength / (1 + 距離)` を、関数として差し替え可能に)。
- 経験のログ出力のフック(`_record` の 1 か所)。

## 4. 応用の候補

### A. 恒常性報酬(homeostatic reward)で、行動に数値を与える
- 動物は、水分・Energy などを一定の範囲に保つ恒常性の生き物。**報酬 = 欲求(drive)の減少**で定義すると、行動の価値が揃う(恒常性強化学習。Keramati & Gutkin の考え方)。
- 案: 欲求 `D = Σ w_i × (1 − 値_i / 最大_i)²`(水分・Energy・スタミナ。w は種の重み)。行動の報酬 `r = D(前) − D(後)`。
  - `drink`: 水分が +5 → 渇いているほど報酬が大きい(渇いていないと小さい)。
  - `eat`: Energy が増えた分。空腹なほど大きい。
  - `rest`: スタミナ・体力の回復。
  - 傷つく: 体力が減る → 負の報酬。
- **記憶に `reward` を持たせると**、「どこで・何をして・どれだけ良かったか」が分かる。単に「飲んだ」より、「渇いているときに飲んだ(大きな報酬)」を強く覚える、といったことができる。

### B. 強さ = 優先度付き経験再生(Prioritized Experience Replay)
- RL の優先度付き経験再生は、**驚き(TD 誤差 |δ|)の大きい経験を優先して再生**する。現仕様の「強さ」(短期記憶の削除の順序、長期記憶の重み)は、この優先度に当たる。
- `strength_mode`:
  1. `random`(現仕様。均一なリプレイに近い)。
  2. `reward`: `強さ = |報酬| × 倍率`(良い経験・悪い経験ほど強く残る)。
  3. `surprise`: `強さ = |報酬 − 長期記憶の期待値|`(予想と違った経験ほど強く残る。たとえば、「覚えていた水の場所に水がなかった」は大きな驚き)。
- **入眠時の整理 = リプレイ**: 整理のとき、短期記憶を「再生」して、長期記憶の価値(§C)を更新する。

### C. 長期記憶 = 価値表(加算の強さから、回数と平均報酬の分離へ)
- 現仕様の「強さを加算」は、**頻度と報酬の大きさが混ざる**。RL の価値表(Q 値)は、**回数 `N` と平均報酬(価値 `V`)を別に持つ**: `N ← N + 1`、`V ← V + α (r − V)`(増分の平均)。
- **非定常な環境**(植物は食べられて消え、再生する)では、`α` を一定(指数移動平均)にして、最近の経験を重く見る。水は静的なので、`V` は安定。
- 想起の score の案: `score = V + c × √(ln N_total / N)`(UCB: 探索ボーナス)。回数が少ない・古い場所に、探索のボーナスを与え、**活用(覚えた良い場所へ行く)と探索(新しい場所を見る)**のバランスを取る。ε-greedy(確率 ε でランダムに探索)も簡単な代替。
- 現仕様との関係: `count`・`last_tick` はすでにある。`value` を足すだけ。強さ(加算)は、「習慣・重要度」として残し、`value` は「報酬の見込み」として別に持つ。

### D. 記憶を方策の入力にする(POMDP の信念状態)
- 視界が限られるので、記憶は**部分観測の補い**。方策(ルール or 学習)への入力に、**「覚えている最良の水の方向・距離」「覚えている最良の食料の方向・距離」**を加える。ルールベースでは、現行の `think` に、「視界に水がなければ、覚えている水へ向かう」を足す形(これが当面の実装)。
- **オプション(時間的に拡張した行動)**: 「覚えている水へ向かう」を、1 つの行動(オプション)として扱う。方策の選択は粗く(12〜20 tick ごと)、実行は経路探索(BFS)が担う。

### E. 信用割当(eligibility trace)
- 報酬が得られたとき(`drank`)、**その直前の経験(`saw_water`、水へ向かった移動)にも報酬を伝える**(TD(λ) の適格度トレース)。短期記憶は、時間順なので、「直前 N 件に、減衰しながら報酬を伝える」を入眠時の整理で行える。
- 効果: 「どの手がかり(見えた水)が、飲水につながったか」を覚える。

### F. 入眠時のモデルベース計画(Dyna)
- 入眠時に、長期記憶の場所を節点にした**認知地図**(場所のグラフ)を作り、**水・食料までの距離場**を計算する(BFS)。翌日の行動は、距離場を引くだけ。計算は、入眠時(1 日 1 回)にまとめるので、毎 tick の負荷がない。
- 経路探索(BFS)の実装と共通の部品(水への距離場)。

### G. 経験のログ(オフライン学習用のデータ)
- `(状態の特徴, 行動, 報酬, 次の状態)` を、JSON Lines などで書き出す(オフ既定)。
- 用途: **オフライン RL・行動模倣(imitation learning)の教師データ**。NPC のルールベース方策を教師にして、学習方策の初期値にする。**PC(人間)のプレイログ**も、模倣学習のデータになる(同意・プライバシーの扱いが要る)。
- **高速なシミュレーションが前提**: 学習には大量のエピソードが要る(`docs/research/headless-speedup-proposal.md`。小さな世界・並列の seed が向く)。

### H. Gym 型のインターフェースと方策のプラグイン
- 環境(`reset`・`step`)として World を包み、1 個体の観測(内部状態 + 視界 + 記憶の要約)と行動空間(移動 4 方向・食べる・飲む・休憩・待機)を公開する。
- 方策(`policy.act(観測)`)を差し替え可能にする。**ルールベース(現行 `think`)をベースライン**に、学習方策と比べる(評価指標: 生存日数、繁殖数、個体数)。
- **サーバの tick 予算(50 ms)内で動く軽い方策**にする(表・線形・小さな決定木)。ニューラルネットの推論は、Python のコアに入れると重いので、外部で学習し、軽量な方策に落とす(蒸留)。
- 捕食者(Fox)と被食者(Rabbit)の**マルチエージェント RL** は、バランス調整にも使える(両者が適応する)。

| 観点 | 内容 |
|---|---|
| 複雑化 | 一度に入れず、段階導入。まず仕様どおりの記憶(乱数の強さ)を実装し、RL の要素は差し替え可能な形で予約する |

| 生態系 | 学習した動物が、植物・捕食関係のバランスを変える(G-2 と合わせて) |

## 6. 段階案と「結果を見て決める」の意味(作者質問 2026-11-09)
**「段階 1 以降は結果を見て決める」とは**: RL 関連の部品(価値・探索ボーナス・認知地図・学習方策)を、最初から全部作ると決めずに、**各段階の終わりに、シミュレーションで効果を測り、次の段階に進むかを判断する**(ゲート方式)という意味。理由: (1) RL の部品は複雑さが増え、報酬設計の失敗(意図しない行動)の危険がある、(2) そもそも、基本の記憶(段階 0)だけで、本来の課題(渇きによる死)が解決するか、まだ分からない、(3) 効果の大きさ(個体数・生存日数)は、測らないと分からない。

| 段階 | 内容 | 終わりに測るもの(判断の材料) | 次へ進む条件の例 |
|---|---|---|---|
| 0 | **仕様どおりの記憶を実装**(乱数 × \|reward\| の強さ、入眠時の整理、丸めた座標、強さ付きの索引)。NPC が記憶を使って水・食料へ向かう(経路探索 BFS と併用) | ① 渇きによる死の割合(小さな世界・複数の seed で、記憶あり / なし)② 記憶の記録件数・長期記憶の大きさ ③ 1 tick あたりの時間 ④ 想起が実際に使われた回数 | 渇き・飢えによる死が、記憶なしより明らかに減り、負荷が許容内 |
| 1 | **報酬の評価**: 表の報酬(固定)に加えて、**恒常性報酬**(欲求の減少。§4 A)を並行して計算し、**ログに出す(行動には使わない)**。headless のログを解析 | 表の報酬と恒常性報酬の相関(例: 渇いていないときの飲水に +10 は妥当か)、行動ごとの報酬の分布、生存との関係 | 報酬の定義が妥当と確認できる(表のまま使うか、恒常性報酬に置き換えるか決める) |
| 2 | 想起の score に、価値(平均報酬)・探索ボーナスを加える(§4 B・C・E)。**A/B 試験**: 現仕様の想起(強さだけ)と比べる | 同じ seed 群(例: 20 個)で、生存日数・個体数の安定・渇きによる死の割合の平均の差(ばらつきを超えるか) | 改善が統計的に有意(例: 平均生存日数が +X% 以上) |
| 3 | 水・食料までの距離場(認知地図)を入眠時に作り、経路探索と統合(§4 F) | 経路の長さ・到達率、負荷 | 到達率が上がり、負荷が許容内 |
| 4 | 経験ログの出力と、Gym 型のインターフェース、方策のプラグイン(§4 G・H) | ログの量・形式、環境の速度(学習に足りるか) | 外部で学習する準備が整う |
| 5 | 外部で学習した軽量な方策の試験(ルールベースと比較) | 生存日数・繁殖数・生態系のバランス | 学習方策が、ルールベースを上回る |
- **各段階は独立に止められる**: 段階 0 で十分なら、そこで止めてよい。
- 段階 0 の `reward` の表(`docs/spec/animal-memory-spec.md` §6.1)は、**作者指示で、強さを決める記憶のための値**(種ごとに固定)。段階 1 の恒常性報酬は、**学習用の報酬の候補**で、両者は別(§7)。

## 7. 報酬の 2 つの意味(整理)
| 呼び方 | 用途 | 決め方 | 時期 |
|---|---|---|---|
| **記憶の reward**(表) | 記憶の強さ(乱数 × \|reward\|)。何を強く覚えるか。`Experience.reward` に残る | (Action, Outcome)の表。種ごとに固定(作者指示) | 段階 0 |
| **学習の報酬**(RL) | 方策を学習するときの報酬信号 | 恒常性報酬(欲求の減少)や、ダメージに比例する負の報酬など。連続値 | 段階 1 以降(検討) |
- 最初は、記憶の reward の表を、そのまま学習の報酬の初期案として使える。大きさに応じた補正(ダメージの量に比例する、など)は、段階 1 で検討する。

## 8. 出来事を状態に含める(作者質問 2026-11-09)

### 8.1 現状(仕様書・コードの確認)
| 項目 | 現状 |
|---|---|
| **出来事の通知**(イベント) | `Region.emit` が、クライアントへの**通知**を作る。種類: `entity_spawned`・`entity_removed`(`reason`: death / eaten / trampled / germinated / hatched / left)・`entity_moved`・`stats_changed`(Player だけ)・`player_died`・`command_rejected`・`seed_germinated`・`reproduced`・`pregnancy_lost`・`fell_asleep`・`woke_up`・`fainted`・`rest_started`・`rest_ended`。世界のイベントログ(リングバッファ)に入り、クライアントが読む。**個体は、このログを読まない**(通知であって、状態ではない) |
| **個体の状態に出来事を表す項目** | **ない**。あるのは、時刻の記録(`last_action_tick`・`last_birth_tick`・`sleep_onset_history`)と、**真偽の旗 `in_combat`・`falling`**(どちらも未実装で、常に偽。`is_safe()` の判定に使うだけ) |
| **ダメージ** | 実装済みなのは、**脱水・飢餓による health の減少**だけ(毎 tick の代謝の中で、`_metabolize`)。**離散的な「ダメージを受けた」出来事は存在しない** |
| **攻撃** | **未実装**。仕様: `docs/spec/animal-states-spec.md` §7(戦闘状態 = こちらが攻撃している、または、攻撃を受けたと認識している間。`combat_recognition_ticks` = 暫定 300 tick)・§8(攻撃力・防御力)。実装計画: `docs/tasks/x_10`、TODO G-26 |
| **落下ダメージ** | **未実装**。仕様: `docs/spec/voxel-spec.md` §6.2(着地エネルギー E = 容積 × 高さ × (g/9.8) × `gravity_k` を、着地したボクセルの全個体に均等配分。落下者は反作用も受ける)。計画: `docs/tasks/x_10` |
| **ダメージの統一的な仕組み** | **仕様のみ**: `voxel-spec` §6.1(`apply_energy(source, targets, E, cause)`: 受けるダメージ = E × (1 − 軽減率)、`toughness` の摩耗、反作用)。`damage` イベント(対象・与えた側・エネルギー・原因)を追加する計画。**脱水・飢餓は、体内の過程なので、この仕組みと統合しない**(§6.3) |
| **刺激による起床** | **未実装**(TODO G-27: 攻撃・ダメージで起きる) |
| **捕食される側** | 食べられると、`entity_removed(reason="eaten", by=…)` で**消える**だけ。被食者は、攻撃を認識しない(逃げる動作もない) |
→ **現状、動物の状態には、出来事が含まれない**。出来事への反応(攻撃されたら逃げる)を方策が学習するには、出来事を状態に含める必要がある。

### 8.2 提案: 出来事を「刺激(Stimulus)」として、状態に反映する
- **用語**: 外から個体に起きる出来事(攻撃・落下・押される・音など)を、内部名 **`Stimulus`**(刺激)とする。サーバのイベントログの「イベント」(クライアントへの通知)とは別の概念(名前の衝突を避ける)。ダメージは `Stimulus` の一種(`Damage`)。
- **伝え方**: ダメージの仕組み(`apply_energy`)・攻撃・落下が、対象の個体の **`Animal.on_stimulus(stimulus)`** を、**その場で(同期的に)**呼ぶ。個体は、状態の項目を更新する。
- **状態の項目(固定長。RL の状態に入れやすい)**:
  | 項目 | 内容 |
  |---|---|
  | `last_damage_tick` / `last_damage_amount` / `last_damage_cause` / `last_damage_source` | 最後に受けたダメージの tick・量・原因(落下・攻撃・…)・相手の ID |
  | `combat_until_tick` | 戦闘状態の終わる tick(攻撃を受けた/攻撃した tick + `combat_recognition_ticks`)。`in_combat` は、これから導く(旗は廃止) |
  | `falling` / `fall_height` | 落下中か、落下の高さ |
  | (任意)直近 K 件の刺激のリング | K = 4 など。複数の出来事への対応 |
  - 「最近ダメージを受けたか」は、`tick − last_damage_tick < 窓` で導く(特徴量として、経過 tick の正規化値)。
- **反応の速さ**: 動物の AI は 12〜20 tick ごとにしか考えない。**ダメージを受けたら、`next_action_tick` を今にして、すぐに考え直させる**(割り込み)。睡眠中の刺激による起床(G-27)も、同じ仕組み。
- **記憶**: `Experience` に記録する(`Outcome` = `hurt`、`subject` = 原因。報酬は表から)。
- **学習の報酬**: ダメージの量に比例する負の報酬を、そのステップに与える。

### 8.3 「Action = none」の扱い(RL の形式との整合)
- RL では、**毎ステップ、必ず action がある**(何もしない = no-op も action)。出来事は、「そのステップに、エージェントが取っていた action に対する、環境の応答(観測 + 報酬)」。
- 提案: 記憶の `Action = none` を、**`idle`(何もしない・待機。no-op)に改める**。`wait`(Player のコマンドにすでにある)に対応する。出来事は、「その時の action(`idle` でも移動でも)」の結果として記録できる。記憶には、「その時していた action」(直前の action)を `action` にする案もある。
- これにより、`Experience = (状態, action, outcome, reward)` が、RL の遷移 (s, a, r, s') に素直に対応する。

### 8.4 状態(RL の観測)の構成(段階 4 以降の設計の見通し)
`状態 s = [内部状態(水分・Energy・体力・スタミナ・覚醒度・欲求の深さ)] + [刺激の特徴(§8.2 の項目)] + [知覚(視界内の水・食料・個体)] + [記憶の要約(覚えている最良の水・食料の方向と距離)] + [時刻・気温]`。出来事への反応と、記憶の活用の両方を、方策が学べる。

### 8.5 実装への影響(落下・戦闘が実装されるとき)
`core/stimulus.py`(新規: `Stimulus`・`Damage`)、`Animal.on_stimulus`、`in_combat`・`falling` の旗を、時間窓つきの状態に置き換える、`ai.think` に割り込み、記憶への記録(`hurt`)、テスト。**落下・戦闘が未実装の今は、状態の項目の定義と、`on_stimulus` の枠を用意するだけでもよい**(段階 0 の範囲外)。
